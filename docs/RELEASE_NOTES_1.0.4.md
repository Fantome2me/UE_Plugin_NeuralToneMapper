# NTM 1.0.4 — 修复 RDG 校验失败（渲染统计从未被写入）

> **发布于 2026-11-17**
> 下载：`NTM1.0.4.zip`（1.39 MB）· UE 5.8 Win64

## 一句话

1.0.3 有一个 **RDG 资源顺序错误**，导致帧统计缓冲区一直读到未写入的纹理。修掉之后，画面亮度与 UE 原生的偏差从 **+0.35 档降到 +0.003 档**，平均误差从 11.7 级降到 **7.5/255**。

---

## 报错

```
Ensure condition failed: Resource->bProduced || Resource->bExternal || Resource->bQueuedForUpload
[RenderGraphValidation.cpp:653]
Pass NTMO::SceneStats has a read dependency on NTMO.Local.Lum, but it was never written to.
```

## 根因：pass 注册顺序错了

RDG 的资源版本是**按 `AddPass` 调用顺序**追踪的，不是按图拓扑重排。读操作注册早了，就绑定到「写入之前」的版本，而这张纹理创建时用了 `FClearValueBinding::None`（没有初始内容）→ 没有生产者。

1.0.3 的代码：

```cpp
711:  Lum[0..3] = GraphBuilder.CreateTexture("NTMO.Local.Lum");   // 创建，无生产者

739:  {  // ← 1.0.3 把这个块挪到了这里（为了给局部校正提供帧均值）
741:      P->NTMOStatsLum = Lum[2];          // ★ 读
749:      AddPass("NTMO::SceneStats", ...);  // ★ 太早了
751:  }

763:  AddPass("NTMO::LocalLum", ...);        // 写 Lum[0]
778:  AddPass("NTMO::LocalDown%d", ...);     // 写 Lum[1..3] ← 真正的生产者在后面
```

**1.0.1 / 1.0.2 没有这个问题** —— 它们的 stats pass 在神经推理分支内部，位置本来就在金字塔之后。1.0.3 搬出去的理由是对的（局部校正 pass 需要帧平均亮度），但**落在了金字塔上方而不是下方**。

## 修复

只移动 pass 的发射位置，`StatsBuffer` 的创建留在原地：

```cpp
735:  创建 StatsBuffer                              // 缓冲区无顺序约束
760:  AddPass("NTMO::LocalLum")                      // 写 Lum[0]
775:  AddPass("NTMO::LocalDown1..3")                 // 写 Lum[1..3]
792:  AddPass("NTMO::SceneStats")                    // ★ 读 Lum[2]，现在有生产者
```

---

## 影响比报错本身严重得多

这个统计缓冲区被三处消费，而它读到的是**未定义数据**：

| 消费者 | 用途 | 被污染后 |
|---|---|---|
| 特征组装 pass | 16 档直方图 + 4×4 分块亮度（网络输入第 17–48 通道） | **网络 32 个输入通道是垃圾** |
| 局部校正 pass | `NTMO_MeanLogLum()` → 局部曝光项 | 局部曝光在未定义数据上运算 |

所以这个 bug **一直在污染神经网络的输入**。修正后同机位、同模型、只差这一处改动：

| 指标 | 1.0.3（统计损坏） | **1.0.4（修复）** |
|---|---|---|
| 网络输出的曲线峰值 | **+0.207 档**（被物理钳制压平） | **−0.132 档**（自然落在面板内） |
| 画面亮度 vs UE | **+0.353 档** | **+0.003 档** |
| 对比度 std 比 | 1.285 | **0.964** |
| 逐像素相关 | 0.934 | **0.9663** |
| 平均误差 | 11.7 / 255 级 | **7.5 / 255 级** |

**我之前汇报的「1.0.3 整体偏亮 +0.31 档」不是模型问题，就是这个 bug。** 修掉之后亮度偏差几乎为零。

## 关于「暗部没变化」——现在有正确答案了

有了正确的统计，局部算子开/关的逐亮度带变化是：

| 输出亮度 | 占比 | dStops |
|---|---|---|
| 0.0–0.05 | 0.1% | −0.001 |
| 0.05–0.15 | 34.8% | +0.002 |
| 0.15–0.35 | 10.1% | **+0.086** |
| 0.35–0.60 | 49.5% | +0.020 |
| 0.60–0.85 | 5.3% | +0.015 |

**这不是 bug，是算子定义使然**：局部曝光只作用于**低于帧均值**的区域。这个测试场景里那 34.8% 的「暗」像素（显示值 0.05–0.15）在 log 域其实并不低于帧均值 —— 它们只是显示得暗，所以按定义不该被提升。

真正该负责扩大暗部动态范围的是**曲线趾部**，不是局部曝光项。

## 测量过但**未采用**：G0（1/2 分辨率）作曝光参考

试过把参考分辨率从 G1（1/4）提到 G0（1/2）：

| 参考 | 0.0–0.05 带 | 0.05–0.15 带 | 整体相关 |
|---|---|---|---|
| G1（采用） | −0.001 | +0.002 | 0.9663 |
| G0（未采用） | **+2.181** | +0.001 | 0.9647 |

G0 能让最深的 0.1% 像素提升 2.18 档，但局部校正**没有时域累积**，把最暗的 0.1% 放大两档等于用暗部噪声闪烁换取一点点阴影层次。整体指标也没有变好，所以放弃。

## 修正过程中暴露的验证流程缺陷

1.0.3 的三次验证（`ntmo_v103run.txt`、`ntmo_bands.txt`、`ntmo_zip103.txt`）**每一次都有这个错误**，但我全部漏掉了，因为当时的 grep 模式是：

```
Shader compilation failures|D3DDebug\]|Fatal error|EnqueueRDG failed
```

**没有包含 RDG 校验的输出。** 1.0.4 起验证模式改为：

```
never written to|Ensure condition failed|RenderGraphValidation
|Shader compilation failures|Fatal error|EnqueueRDG failed|was never produced
```

并且扫描 `Saved/Logs` 下最近的日志，而不只是我重定向的那一份。
