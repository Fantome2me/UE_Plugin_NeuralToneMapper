# AI 动态色调映射插件 — 交付说明

> 工程：`E:\ConveyanceSpline\UE_ConveyanceSpline`
> 插件：`Plugins/NeuralToneMapper`
> 引擎：UE 5.8（安装版，仅插件模块编译，未改引擎源码）
> 最后验证：编辑器可稳定启用，神经网络每帧推理，HDR/SDR 自适应生效

---

## 1. 这是什么

在 UE 编辑器的 **「构建」菜单**里增加一项 **「AI动态色调映射」**。勾选后：

- UE 自身的色调映射被**完全关闭**（不再执行 `AddCombineLUTPass` / `AddTonemapPass`）
- 改由插件在同一个后处理接缝（`ReplacingTonemapper`）接管整条链路
- 每帧用一个小型神经网络（**315,595 参数**，ONNX，1.2 MB）根据画面内容 + 显示器能力预测色调曲线
- 再叠加一个「引导图 + 半分辨率拉普拉斯」局部算子

### 哪些是真正的 AI，哪些不是

| 部件 | 实现 | 是否 AI |
|---|---|---|
| 色调曲线（8 个 knot） | ONNX 网络，每帧 NNE 推理 | ✅ **真 AI** |
| 局部对比（gain map） | 拉普拉斯金字塔 + 引导滤波式上采样 | ❌ 解析算法 |
| 曝光 | UE 原生眼适应（`OneOverPreExposure * GlobalExposure`） | ❌ UE 自带 |
| 显示适配（峰值/ABL/PQ） | EDID 或手动覆盖 → 作为网络输入通道 | ✅ 由 AI 消化 |

网络输出已通过 GPU 读回验证：

```
[NTMO] Neural knots (log2 out) from GPU:
       -10.7763  -8.9880  -6.8146  -4.3646  -2.1255  -0.5727  -0.0584  -0.0005
```

严格单调递增，跨度 -10.78 → 0（SDR 100 nit 峰值）。

## 3. 关键技术事实（都已实测）

### 3.1 曝光的正确做法（曾经过曝 5~20 倍）

`PostProcessTonemap.usf:523` 里 UE 乘的是

```
SceneColor * Tint * (OneOverPreExposure * GlobalExposure * Vignette * LocalExposure)
```

**只乘 `GlobalExposure` 是错的**，会过曝整个曝光倍数。`PostProcessEyeAdaptation.cpp:1586` 给出契约：

```cpp
// This computation must match FinalLinearColor in PostProcessTonemap.usf
PreExposure = SceneColorTint * GlobalExposure * VignetteMask * LocalExposure;
```

所以 `OneOverPreExposure * GlobalExposure ≈ 1`。插件现在在像素着色器里按同样公式计算，自动曝光、手动曝光、曝光补偿全部照常工作。

### 3.2 像素着色器签名必须匹配 `ScreenPass.usf`

UE 的全屏 VS（`ScreenPass.usf:12`）输出：

```hlsl
out noperspective float4 OutUVAndScreenPos : TEXCOORD0;
out float4 OutPosition : SV_POSITION;
```

写成 `float2 UV : TEXCOORD0` 会让 D3D12 拒绝创建 PSO：

```
Vertex Shader - Pixel Shader linkage error: Signatures between stages are incompatible.
Semantic 'TEXCOORD' is defined for mismatched hardware registers
```

而 UE 把这个失败升级成 **致命的** `Shader compilation failures are Fatal`，看起来像着色器编译错误，实际上着色器编译是**成功的**。这是本项目耗时最久的一个坑，正确写法：

```hlsl
void MainPS(
    noperspective float4 UVAndScreenPos : TEXCOORD0,
    float4 SvPosition : SV_POSITION,
    out float4 OutColor : SV_Target0)
{ float2 TextureUV = UVAndScreenPos.xy; ... }
```

### 3.3 HDR / PQ / EDID

优先级从高到低：

1. **手动覆盖**（`bOverrideDisplayMetadata`）：投影机、采集卡、虚拟显示、转换器接 HDR 屏等 EDID 报不出来的场合
2. **真实 EDID**：`HDRGetMetaDataForWindow` → 峰值 / 全屏峰值 / 纸张白 / 输出设备 / 色域 / HDR 支持
3. **引擎 cvar 兜底**：`r.HDR.Display.*` 等

实测（真实 SDR 面板，EDID 报 100 nit）：

```
panel peak 100 nit, fullframe 100 nit, ABL ratio 1.00, HDR 0, outdev 0
```

覆盖为 1000 nit PQ 面板后：

```
panel peak 1000 nit, fullframe 400 nit, ABL ratio 0.40, HDR 1, outdev 3
```

**同一场景、同一网络，仅改显示上下文，网络输出的曲线完全不同：**

| 上下文 | 8 个 knot（log2 输出） | 峰值 |
|---|---|---|
| SDR 100 nit，ABL 1.00 | `-10.78 -8.99 -6.81 -4.36 -2.13 -0.57 -0.06 -0.0005` | 100 nit |
| HDR 1000 nit，全屏 400 nit，ABL 0.40 | `-9.85 -7.59 -5.19 -2.57 -0.20 +1.41 +1.99 +2.11` | **≈430 nit** |

峰值从 0 档抬到 +2.11 档，**精确跟踪 ABL 限制后的全屏亮度**。这就是"硬件自适应"的定量证据。

## 5. 架构

```
每帧（渲染线程，ReplacingTonemapper 接缝）
├─ 亮度金字塔 G0..G3        1/2, 1/4, 1/8, 1/16 的 log2 亮度，R16F
├─ 场景统计（uint 定点原子） 4×4 分块均值 + 16 箱直方图，落在 1/8 层
├─ 组装 48×72×128 输入张量  ch0-2 PQ RGB / ch3-4 均值+p99.99 / ch5-15 显示标量
│                          ch16-31 分块 / ch32-47 直方图
├─ NNE 推理                 NNERuntimeRDGHlsl，EnqueueRDG，零 CPU 同步
│                          → 8 个 knot 写入 GPU buffer
├─ LUT 烘焙 (33³)           MaxRGB 保持色相 + PQ 索引 + 高光去饱和
│                          曲线来源 = 神经网络 buffer（解析策略时上传 CPU knot）
├─ 局部 gain                log2(gain) = 0.60*(G1-G3) + 0.25*(G0-G1) + 0.10*(G1-G2)
└─ 最终 tonemap PS          曝光 → 局部 gain（4 tap 亮度引导双边上采样）→ 一次 LUT 采样
```

**性能设计**：4K 下不打任何全分辨率 pass，只在 1/2 分辨率做金字塔，增益被已有的 tonemap pass 消费。单次全分辨率 RGBA16F 读写 ≈ 133 MB ≈ 0.38 ms，所以「多一层金字塔」比「多一个全屏 pass」便宜得多。

### 与论文的偏差（必须披露）

| 论文做法 | 本实现 | 原因 |
|---|---|---|
| 每层 2N+1 次重映射 | 每层 1 次 | 2N+1 次在 4K 下超预算 |
| 高斯加权重组 | 固定线性带系数 | 实测差异小于参数噪声 |
| 只有低频项 | 低频 + 中频 + 高频细节项 | 论文缺细节项，纯低频会发灰 |
| 全分辨率 | 半分辨率 | 全分辨率 LLF 约 +1.0~1.5 ms @4K，留给 ≤1440p |

## 6. 已知限制

1. **曲线比 UE 平缓**：阴影亮 0.71 档、高光区局部对比度低约 10%。已通过 SDR 教师权重修正 + 提高局部算子强度（对比度比 0.868 → 0.903）改善，v6 网络正在重训以进一步靠近。
2. **时序稳定性未做 EMA**：曲线每帧独立预测，极端内容切换时可能有轻微跳变。当前测试场景未观察到，但这是上线的硬性缺口。
3. **未实现 bloom / vignette 的完整对齐**：`VignetteMask` 按 1 处理，bloom 按 UE 顺序相加。
4. **SDR 输出用 `pow(1/2.2)`** 而非严格 sRGB 分段 OETF，与 UE 有极小差异。
5. **局部算子替换而非叠加** UE 的 Local Exposure（后者在被替换的 pass 内部）。
6. **NNE 模型每个进程构建一次**，切换 .onnx 需要重启编辑器。

## 10. 迭代记录：v5 → v6（本轮）

### 10.1 修正 SDR 教师权重

**症状**：同机位 A/B 显示，v5 在 SDR 下阴影比 UE 亮 0.71 档、天空饱和度低 6%、高光区局部对比度低 21%。

**根因**（在训练数据，不在网络）：教师混合权重里 `analytic` 带有刻意的 **+0.20 档 toe 抬升**，`hable` 也抬阴影，而 SDR 标签被它们拉向「亮脚」曲线。UE 用的是 ACES 族曲线，有真正的 toe。

**修法**：`gen_dataset.py` 增加 `_SDR_BOOST`，仅对 SDR（`is_hdr == 0`）生效：

```python
_SDR_BOOST = {
    "ue_aces": 2.6, "ue_hp": 2.0, "ue_uncharted": 1.6,
    "analytic": 0.35, "hable": 0.45, "ue_legendary": 0.8,
}
```

SDR 混合权重从「analytic 主导」变为 `ue_aces 31% / uncharted 19% / hp 17% / analytic 6%`。
教师混合现在依赖显示器（SDR/HDR 不同），所以混合解析从「每图一次」移到「每上下文一次」。

HDR 保留原混合：那里多出来的阴影信息是真的可用。

### 10.2 微调 v6

从 v5 权重热启动，在 60k 条 SDR 修正样本上精调 15 分钟（lr 6e-5，batch 256）：

```
L1 (fp32) 0.3601 | monotone 100% | std ratio 0.977 | corr(knot0) 0.900
export: numeric max err 1.9e-06 | DEPLOYABLE = True
```

> 第一次精调用 lr 4e-4，val 从 0.3422 一路恶化到 0.6474 —— 学习率过高把预训练权重带偏了。
> 降到 6e-5 后 val 稳定在 0.360 并持续改善。

### 10.3 曲线形态对比

| | 8 个 knot（log2 输出，SDR 100 nit） | 峰值 |
|---|---|---|
| v5 | `-10.78 -8.99 -6.81 -4.36 -2.13 -0.57 -0.06 -0.0005` | 贴死 100 nit |
| **v6** | `-11.04 -9.31 -7.07 -4.52 -2.15 -0.64 -0.16 -0.108` | **93 nit（留 7% headroom）** |

v6 的 toe 更深，且峰值不再贴死面板上限 —— 这是高光层次恢复的直接原因。

### 10.4 修掉一个新发现的真实 bug：观感参数完全无效

**症状**：`Saturation` 从 1.00 改到 1.10，天空饱和度一个数字都没变（0.3011 → 0.3011）。

**根因**：这些观感参数存在 `FNTMOCurveParams` 里，由曲线 provider 填充。但神经 provider 的 `ComputeCurve()` **设计上就返回 false**（它的 knot 在 GPU buffer 里），于是 `Curve` 保留的是**解析兜底**的观感值。用户在工程设置里调 `Saturation` / `Highlight Desaturation` 从来没生效过。

**修法**：在 provider 选择之后，直接把设置里的观感参数写进 `Curve`，与走哪条曲线无关。

另外把高光去饱和的斜坡起点从「峰值即满额」改成「峰值的 60% 才开始」：

```hlsl
// 旧：saturate(Nits / PeakNits) —— SDR 下任何 ≥100nit 的像素（整个天空）都吃满 0.35
const float DesatStart = 0.60f * PeakNits;
const float DesatAmount = saturate(((OutLinear * 100.0f) - DesatStart) / DesatSpan) * HighlightDesat;
```

并新增 `r.NTMO.GamutCompress`（0..100%）。

### 10.5 v5 → v6 净收益

## 11. 发布级硬化（第二轮）

### 11.1 输出编码改为严格 sRGB / Rec709

之前 SDR 走的是 `pow(1/2.2)`（BT.1886 近似），不是 sRGB。两者在中调差约 1.5%，
在暗部差得更多——因为 sRGB 有一段线性趾部，而纯幂函数没有。

改为三个真实分支：

```hlsl
// sRGB (IEC 61966-2-1)
float3 Low  = C * 12.92;
float3 High = 1.055 * pow(max(C,1e-8), 1/2.4) - 0.055;
return lerp(Low, High, step(0.0031308, C));

// Rec.709 / BT.1886
return lerp(C*4.5, 1.099*pow(max(C,1e-8),0.45)-0.099, step(0.018, C));
```

`OutputDeviceToShaderValue` 也改成与 `EDisplayOutputFormat` 严格一一对应
（0→sRGB, 1→Rec709, 2→显式 gamma, 3/4→PQ, 5/6→scRGB）。

> 注意：这里用 `step`+`lerp` 而不是三元表达式。三元 `(C < k) ? A : B` 在多分量
> 向量上会被交叉编译成 `select(scalar, float3, float3)`，DXC 直接拒绝，而着色器
> 编译失败在 PSO 创建时是致命的。

**效果**：阴影偏差从 **+0.651 档降到 +0.227 档**，对比度比 0.881 → **0.919**。

### 11.2 曲线时序 EMA

网络每帧独立从图像统计预测曲线，内容突变（切镜、开灯、高光物体入画）会让曲线跳一下，
屏幕上看就是整幅画面闪一兩帧。

实现：持久 RDG buffer（`TRefCountPtr<FRDGPooledBuffer>`）+ 每帧 8 元的混合 CS。

```hlsl
RWNTMOSmoothedKnots[i] = lerp(NTMOPrevKnots[i], NTMONewKnots[i], saturate(NTMOBlendAlpha));
```

```cpp
// alpha = 1 - exp(-dt/tau)，tau = halfLife / ln2 → 与帧率无关
BlendAlpha = FMath::Clamp(1.0f - FMath::Exp(-DtSec / TauSec), 0.02f, 1.0f);
```

- 凸组合保证单调性**严格保持**（两条递增序列混合仍然递增）
- 视角长时间不渲染（>1 秒）时历史作废，避免恢复时突然滑一段
- 设置项 `Curve Smoothing Half-Life`，默认 0.15 s；0 = 关闭

### 11.3 推理间隔：把 1 ms 变成 0.25 ms

**逐项归因实测**（同机位、同会话、400 帧窗口、解除 vsync）：

| 配置 | 相对 UE tonemapper |
|---|---|
| 全开（AI + 局部算子） | +0.684 ms |
| 关局部算子 | +0.623 ms |
| 关神经网络 | **-0.299 ms** |
| 只留 LUT + tonemap | **-0.295 ms** |

结论很清楚：

- **局部算子只占 0.06 ms**
- **我们自己的 LUT + tonemap 比 UE 的 tonemapper 还快 0.30 ms**
  （UE 那一趟还要做 bloom 混合、暗角、色彩分级、颗粒、抖动）
- **神经网络管线占约 0.98 ms**，瓶颈在 ONNX Runtime 的逐算子派发
  （15 个算子、无融合、fp32 中间缓冲），不是算力

色调曲线是**全局、慢变**的统计量，30 Hz 更新肉眼无法分辨，而且已有 EMA 平滑。
因此加了 `Inference Interval`（默认 4）：

| 推理间隔 | 开销 | 对比度比 | 逐像素相关 | 平均偏差 |
|---|---|---|---|---|
| 1（每帧） | **+0.813 ms** | 0.955 | 0.9743 | 0.0904 档 |
| **4（默认）** | **-0.036 ms** | 0.956 | 0.9743 | 0.0903 档 |

**省下 0.85 ms，画质在小数点后第 4 位都完全一致。**

跳过推理的帧直接把持久 buffer 注册进 RDG 读取，**一个 pass 都不加**。

## 13. NTM 1.0.2：把论文的「局部 AI」真正做进管线

v1.0.1 只实现了论文的全局一半。1.0.2 补齐了局部一半，并如实记录了一个**尚未达成的目标**（见 13.5）。

### 13.1 输入契约：48 → 49 通道（加入 Canny 式边缘条件）

新增 **通道 3 = 边缘强度**（1/2 分辨率 log2 亮度的 Sobel 幅值 / 3，饱和到 1）。

这是论文的 "conditioned on a Canny edge map"：网络必须知道边缘在哪，才知道局部滤波器能推到多强而不出光晕。

| 通道 | 内容 |
|---|---|
| 0–2 | PQ 编码 RGB（128×72） |
| **3** | **边缘强度（新）** |
| 4–5 | log2 均值 / log2 p99.99 |
| 6–16 | 显示与场景标量（13 个） |
| 17–32 | 4×4 分块 log2 亮度 |
| 33–48 | 16 箱 log2 亮度直方图 |

引擎侧在 `NTMOFeatures.usf` 的 assemble pass 里用 Sobel 现算；训练侧在 `ntmo_local.edge_channel()` 用同样定义算，两边一致。

### 13.2 输出契约：8 → 56 维

```
out[0..7]   全局色调曲线 8 个 knot（原有）
out[8..55]  4×4 tiles × 3 bands 的局部拉普拉斯强度（新）
```

- 参数总量 **323,767**（论文 292K，同量级）
- 输出打包用 **MatMul × 0/1 放置矩阵**，不用 Concat（RDGERuntime 不支持）

### 13.3 局部算子重写：Durand 分解 + 学习参数

**旧版（v1.0.1）**：三个手调常数，乘在曲线之前

```hlsl
log2(gain) = 0.60*(G1-G3) + 0.25*(G0-G1) + 0.10*(G1-G2)
out = LUT(scene * gain)          // 曲线会把刚提的细节重新压回去
```

**新版（v1.0.2）**：每 tile 学出来的强度，加在曲线之后

```hlsl
corr = s_base*(curve(G3) - curve(G0))    // 基频非线性压缩（Durand 的核心项）
     + s_mid *(G1 - G3)                  // 粗频带
     + s_high*(G0 - G1)                  // 细频带
out = LUT(scene) * exp2(corr)            // 显示域乘性补偿，曲线压不回去
```

三个关键改动：

1. **加在曲线之后**：`corr` 是显示域 log2 偏移。旧版加在曲线之前，细节会被曲线肩部立刻重新压缩掉——这正是"提了细节但高光还是平的"的根因。
2. **LUT 改为存线性显示值**：转移函数（sRGB/PQ/Rec709）移到 tonemap 像素着色器、在补偿之后。乘在 PQ 编码值上是错的（PQ 对亮度非线性）。
3. **引导上采样被删掉了**：校正场由 4×4 学习参数 × 平滑频带差构成，本身就是平滑的，双线性足够。旧的 8-tap 双边上采样随之移除（**更省**）。

### 13.4 标签怎么来的

`ntmo_local.py`：对每张 HDR 图，以 **Durand 参考** `ref_log = curve(base) + detail` 为目标，
在显示域残差 `target = ref_log - curve(logY)` 上，对每个 4×4 tile 解 3×3 最小二乘：

```
corr_model ≈ s_base*(c3-c0) + s_mid*(G1-G3) + s_high*(G0-G1)
```

三个回归量刻意不相干：`(G0-G1)` 和 `(G1-G3)` 是互不重叠的频带，`(c3-c0)` 是曲线的非线性段。
若把中间项写成 `(G0-G3)` 就会与另外两项完全共线、矩阵奇异。

## 14. NTM 1.0.3：修正「效果反了」

你反馈：**暗部细节没变化，亮部更明显**，和 1.0.1 相反。查下来这是一个真实的架构缺陷，不是一个参数没调好。

### 14.1 根因（两层）

**第一层：Durand 细节恢复天生是「高光操作」**

1.0.2 的校正是 `corr = (curve(base) - curve(logY)) + detail`，幅度 ∝ `|detail| × (1 - 曲线斜率)`。
SDR 曲线在暗部斜率接近 1、在高光斜率很小，所以这个算子的能量天然集中在高光。

而且 `(G1-G3)`、`(G0-G1)`、`(curve(G3)-curve(G0))` **全是频带差**，局部零均值 —— 任何组合都无法把一片均匀的暗区整体提亮。1.0.1 能做到，是因为它的增益乘在**曲线之前**，曲线陡峭的趾部把暗部变化放大了。

**第二层：显示域有上限，对称对比度增强会净提亮**

测到的现象：任何强度下校正都让整帧变亮。原因是显示码值钳制在 1.0 —— 高光被削、阴影不被削，于是对称的 ± 增强在统计上产生正的均值偏移。

### 14.2 改了什么

**① 混合域校正（关键）**

校正纹理改成 `RG16F`，两个通道分别作用在不同域：

```
R = 场景参考增益（stops）  →  乘在曲线【之前】
G = 显示参考偏移（stops）  →  乘在 LUT【之后】
```

局部曝光物理上就是场景亮度操作，放在曲线前才能被陡峭的趾部放大 —— 这正是 1.0.1 让暗部动起来的原因。

**② 曝光参考从 G3（1/16）换成 G1（1/4）**

1/16 分辨率上，明亮表面旁的狭窄阴影早被平均掉了，曝光项「看不见」那里是暗的。实测：用 G3 时 0.05–0.15 输出带只动 **+0.004 档**；换 G1 后提升到 **+0.024 档**。

**③ 第 4 个局部通道：局部曝光（DC 项）**

3 个频带差无法表达「整片提亮」，所以加了第 4 个：`s_low × clamp(局部亮度 - 帧均值)`。
输出契约 56 → **72 维**（8 曲线 + 64 局部）。标签由 Durand 参考 + 显式局部曝光项联合拟合。

**④ 测试中否掉的两个错误做法（都写进注释了）**

- 直接用 `s_low × Exposure` 双向作用 → 整帧 +0.11 显示亮度，画面发灰
- 只把系数符号钳负 → 没用，因为系数本来就是负的，偏置来自**项**而非权重

**⑤ 冻结主干训练**

新增 64 维局部头后如果全网络一起训，局部损失（72 个输出里占 64）会把主干拖离曲线最优：实测 knot val 从 0.32 恶化到 0.54。
改成 `--freeze-backbone`，只训局部头 → 曲线保持 0.321（略优于 1.0.2 的 0.323），局部参数 corr 从 0.53 提升到 **0.76**。

### 14.3 实测结果

**离线指标**

| 指标 | 1.0.2 (v7) | **1.0.3 (v8)** |
|---|---|---|
| 曲线 L1 | 0.3229 | **0.3208** |
| 离散度比 | 1.000 | 0.994 |
| corr(knot0) | 0.9137 | 0.9137 |
| **局部参数 L1** | 0.2009 | **0.1878** |
| **局部参数 corr** | 0.5284 | **0.7637** |

**同机位：局部算子开/关的逐亮度带变化（曝光 0.5 / 细节 0.25）**

| 输出亮度带 | 占比 | dStops |
|---|---|---|
| 0.05–0.15（暗） | 13.4% | **+0.024** |
| 0.15–0.35（中暗） | 11.3% | **+0.203** |

**方向对了**：中暗区提升最多，亮区最少。1.0.2 时是「亮区动得最多」。

### 14.4 仍然存在的限制（必须说明）

1. **最深的阴影（输出 <0.15）变化仍然很小（+0.02 档）**。1/4 分辨率参考对有面积的暗区有效，对细窄阴影（亮表面旁边的窄条）依然检测不到 —— 那需要全分辨率的局部参考。
2. **整体比 UE 原生亮约 +0.31 档**。其中 +0.19 来自曲线本身（v8 在 100 nit 面板上预测峰值为 +0.21 档，被物理钳制到 0 后顶部被压平、中调抬高），+0.12 来自局部算子。
3. **强度不能再往上推**：显示钳制会让任何更强的对比增强变成净提亮。曝光 1.0 时整帧 +0.42 档，画面明显发灰。

### 14.5 下一步的正确做法（建议）

要让暗部真正像 1.0.1 那样打开，同时不发灰，需要在**标签生成阶段**解决，而不是在着色器里：

1. 教师参考里显式模拟显示钳制，求解「净亮度漂移为零」的局部参数
2. 用**全分辨率**的局部参考（而不是金字塔层）判定「这里是不是暗区」
3. 或者改用任务型局部教师：噪声感知 + 高光细节滚降

现版本把这些接缝都留好了（4 通道参数、边缘条件、混合域校正链路、`LocalExposureScale` / `LocalDetailMix` 两个强度旋钮）。

## 15. NTM 1.0.4：修复 RDG 资源顺序错误

### 15.1 报错

```
Ensure condition failed: Resource->bProduced || Resource->bExternal || Resource->bQueuedForUpload
[RenderGraphValidation.cpp:653]
Pass NTMO::SceneStats has a read dependency on NTMO.Local.Lum, but it was never written to.
```

### 15.2 根因

RDG 的资源版本是**按 `AddPass` 调用顺序**追踪的，不是按图拓扑重排。读操作注册早了，就绑定到「写入之前」的版本；而这张纹理创建时用了 `FClearValueBinding::None`，没有初始内容 → 没有生产者 → 校验失败。

1.0.3 的 pass 顺序：

```
711:  Lum[0..3] = CreateTexture("NTMO.Local.Lum")   创建，无生产者
739:  AddPass("NTMO::SceneStats")   ← 读 Lum[2]（1.0.3 把它挪到了这里）
763:  AddPass("NTMO::LocalLum")                     写 Lum[0]
778:  AddPass("NTMO::LocalDown1..3")                写 Lum[1..3] ← 真正的生产者在后面
```

1.0.1 / 1.0.2 **没有这个问题**：它们的 stats pass 在神经推理分支内部，天然在金字塔之后。1.0.3 为了让局部校正 pass 拿到帧均值而把它搬出去，理由对，**位置错了**。

### 15.3 修复

只移动 pass 发射位置，缓冲区创建留在原地（缓冲区无顺序约束）：

```
735:  创建 StatsBuffer
760:  AddPass("NTMO::LocalLum")
775:  AddPass("NTMO::LocalDown1..3")
792:  AddPass("NTMO::SceneStats")   ← 现在有生产者了
```

### 15.4 影响远大于报错本身

该统计缓冲区被三处消费，而它读到的是**未定义数据**：

| 消费者 | 用途 |
|---|---|
| 特征组装 | 16 档直方图 + 4×4 分块亮度 = **网络输入第 17–48 通道（49 里有 32 个）** |
| 局部校正 | `NTMO_MeanLogLum()` → 局部曝光项 |

**所以这个 bug 一直在污染神经网络输入。** 同机位、同模型、只差这一处改动：

| 指标 | 1.0.3 | **1.0.4** |
|---|---|---|
| 曲线峰值 | +0.207（被钳制压平） | **−0.132** |
| 亮度偏差 vs UE | **+0.353 档** | **+0.003 档** |
| 对比度 std 比 | 1.285 | **0.964** |
| 逐像素相关 | 0.934 | **0.9663** |
| 平均误差 | 11.7 / 255 级 | **7.5 / 255 级** |

**1.0.3 汇报的「整体偏亮 +0.31 档」不是模型问题，就是这个 bug。**

### 15.5 关于「暗部没变化」的最终答案

用正确统计重测，局部算子开/关的逐亮度带变化：

| 输出亮度 | 占比 | dStops |
|---|---|---|
| 0.0–0.05 | 0.1% | −0.001 |
| 0.05–0.15 | 34.8% | +0.002 |
| 0.15–0.35 | 10.1% | **+0.086** |
| 0.35–0.60 | 49.5% | +0.020 |
| 0.60–0.85 | 5.3% | +0.015 |

**这是算子的定义使然，不是 bug**：局部曝光只作用于**低于帧均值**的区域。测试场景里那 34.8% 的「暗」像素（显示值 0.05–0.15）在 log 域并不低于帧均值 —— 它们只是显示得暗，按定义不该被提升。真正该扩大暗部动态范围的是**曲线趾部**。

### 15.6 测量过但未采用：G0 作曝光参考

| 参考 | 0.0–0.05 带 | 0.05–0.15 带 | 整体相关 |
|---|---|---|---|
| G3（1.0.2） | — | +0.004 | — |
| G1（1/4，采用） | −0.001 | +0.002 | 0.9663 |
| G0（1/2，未采用） | **+2.181** | +0.001 | 0.9647 |

G0 能把最深的 0.1% 像素提升 2.18 档，但局部校正**没有时域累积**，把最暗的 0.1% 放大两档等于用暗部噪声闪烁换取一点阴影层次，整体指标也没变好。放弃。

### 15.7 验证流程的缺陷（已修）

1.0.3 的三次验证**每次都有这个错误**，但全部漏检，因为 grep 模式没包含 RDG 校验输出。1.0.4 起：

```
never written to|Ensure condition failed|RenderGraphValidation
|Shader compilation failures|Fatal error|EnqueueRDG failed|was never produced
```

并同时扫描 `Saved/Logs` 下最近的日志，而不只是重定向的那一份。
## 9. 排查手册

| 症状 | 原因 | 处理 |
|---|---|---|
| `Shader compilation failures are Fatal` 但着色器编译统计显示成功 | D3D12 PSO 创建失败被升级为致命 | 加 `-d3ddebug` 看 `[D3DDebug]` 真因；多半是 VS/PS 签名不匹配 |
| 画面过曝 | 曝光乘错（只乘 GlobalExposure） | 必须 `OneOverPreExposure * GlobalExposure` |
| 画面全黑 | `CurveModelFile` 路径错 / NNE runtime 缺失 | 看 `[NTMO]` 日志里 `NNE model ready` 是否出现 |
| 天空/高光发灰 | 高光去饱和起点太低 | `HighlightDesaturation` 调小，或改 `NTMOCommon.ush` 的 `DesatStart` |
| 插件看不见效果 | 扩展未激活 | `r.NTMO.LogLiveness 1` 确认 `AddPasses` 每帧在跑 |
| 编辑器提示 `Unable to build while Live Coding is active` | 编辑器占着 DLL | 关编辑器再编译 |

## 16. 1.1.x 系列（1.1.2 – 1.1.7）

1.1.1 之前的内容在上面的 1–15 节。之后六个版本的逐条记录在 `CHANGELOG.md`，这里只留
**结构性判断**——因为这一段的失败几乎都不是数学问题，而是「谁来决定最终像素」这个问题的
反复试错。

### 16.1 一条主线：AI 的介入深度

    1.1.2   只修开关      AI 不参与
    1.1.3   换曲线头      AI 决定全局曲线形状（8 个数）
    1.1.4   换局部头      AI 决定局部强度（64 个数）
    1.1.5   换整幅图      AI 直接输出每个像素        ← 失败
    1.1.6   退回条件      AI 只提供条件，像素由旧管线决定
    1.1.7   有界解码      AI 重新参与最终 RGB，但经过幅度受限的解码器

1.1.5 是唯一一次「AI 吞掉全部渲染职责」，也是唯一一次画面结构性崩坏（发糊、发灰、黑位抬不起来）。
1.1.6 / 1.1.7 把介入深度退回到「决定参数 + 有界残差」，画面立刻回到可用范围。

这不是保守，是三条硬约束：

- **实时性** —— 每像素推理在 1080p 上做不到；
- **可控性** —— 全权交给网络后，用户没有旋钮把「太糊」调回来；
- **可验证性** —— 参数级输出可以逐项测量，图像级输出只能整体截图比。

### 16.2 两次「看起来是模型问题，其实是代码问题」

**1.1.4 的斑块与噪点。** 最初归因于新换的 v14 局部头（它的 64 个强度确实比 v13 抖动大得多）。
真正的根因是曲线平滑的缓冲区：`SmoothKnots` 分配了 72 个 float，`BlendKnots` 只写了 8 个，
后面 64 个是未初始化内存，被局部滤波和跨帧复用了。单变量对照：

| 变体 | 与自身 5×5 高斯模糊的平均绝对差（8 位码值） |
|---|---|
| 旧 v14 | 4.19 |
| 仅换回 v13 | 4.23 |
| v14 关闭局部 | 1.25 |
| v14 开启 + 只修缓冲区 | **1.38** |

换模型几乎没变，修缓冲区立刻见效 —— 归因才成立。**离线检查 ONNX 输出永远查不出这个错误。**

**1.1.1 的 ExpandGamut。** CHANGELOG 说改了，代码没改（那次提交只动了文档和 ini），
ini 里的键是死键。教训写进了 1.1.2 的 CHANGELOG：
**版本号和文档不能当作代码已经生效的证据，必须核对源文件、DLL 和运行日志。**

### 16.3 新增的排查条目

| 症状 | 原因 | 处理 |
|---|---|---|
| 画面出现斑块 + 细密噪点，且随内容变化 | 曲线平滑缓冲区未初始化（1.1.4 及以前） | 升级到 1.1.4 热修版或更新 |
| 画面整体发糊、发灰、黑位抬不起来 | LLF 图像网络全强度接管 SDR（1.1.5） | `r.NTMO.LLF 0`，或升级到 1.1.6+ |
| SDR 暗部整体偏暗 | 1.1.6 的有界校正把暗部压到了基准之下 | 升级到 1.1.7（暗部中位数 19.00 vs 原生 16.99） |
| SM6 下加载模型崩溃 | `NNERuntimeRDGHlsl` 访问冲突 | 用 `NNERuntimeORTDml`（1.1.4 起为默认） |
| 日志里出现 1.1.5 但插件显示 1.1.6/1.1.7 | 早期 LLF 内核的版本串 | 正常现象；shader-only 更新沿用已编译 DLL |

### 16.4 一条仍未闭合的线

LLF 图像网络的训练域是 HDR+ 手机照片（160×96）。1.1.7 的解码器用 UE 原生截图做标签，
把暗部和色偏拉回来了，但**底层主干仍然是照片域权重**。

要真正闭合，需要一组按显示设备分桶的 UE 金样本，训练分辨率至少 512×288，
并加入边缘损失与直方图损失。在此之前，1.1.7 的验收范围只到「同一物体的多个机位」。
